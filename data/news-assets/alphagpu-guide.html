처음이라면: Dockerfile과 Docker Compose의 차이

Dockerfile = 개발 환경을 만드는 레시피. NVIDIA CUDA·PyTorch가 들어 있는 기본 이미지에 필요한 Python 패키지를 설치합니다.

Docker 이미지 = 레시피로 만든 실행 환경. 프로젝트마다 패키지를 분리할 수 있습니다.

Docker Compose (compose.yaml) = 실행 설정서. 이미지를 빌드하고 GPU를 연결하며, 서버 폴더를 컨테이너에 연결하고 시작·종료합니다.

실행 흐름: GitHub에서 코드 받기 → 프로젝트 폴더로 cd → Dockerfile/Compose 준비 → docker compose up -d --build → GPU 검증 → 연구 코드 실행.

01. 개발 환경 운영 원칙

기존에는 Anaconda·venv·수동 CUDA 설치 등 다양한 방법으로 개발 환경을 구성해 사용자마다 라이브러리 버전이 달라지고, 프로젝트를 다른 서버에서 재현하기 어려웠습니다. 이를 줄이기 위해 다음 원칙을 적용합니다.

  • GitHub: IMSI Lab Organization에 프로젝트별 Repository를 생성하고 소스코드와 환경 설정을 버전 관리합니다.
  • Dockerfile: CUDA, PyTorch, Python 및 추가 패키지를 포함하는 프로젝트 실행 이미지를 정의합니다.
  • Docker Compose: 컨테이너 실행, GPU 사용, 공유 메모리, 데이터 연결을 한 파일로 관리합니다.
  • 사용자별 저장소: 각자 할당된 /home/<username> 내부에서 프로젝트를 생성하고 운영합니다.
  • 데이터 분리: 대규모 원본 데이터·모델 체크포인트는 GitHub가 아니라 승인된 서버/NAS 경로에 저장합니다.

원칙적으로 새 AI 연구 프로젝트에는 Conda 또는 venv를 추가로 만들지 않습니다. 프로젝트별 패키지가 다르다면 각 프로젝트의 Docker 이미지에 설치합니다. 이 정책은 호스트 서버의 Python 환경을 보호하기 위한 것이지, 모든 프로젝트가 반드시 동일한 Python 패키지 버전을 사용해야 한다는 의미는 아닙니다.

빠르게 진행하려면 각 장의 핵심 명령만 따라가세요. 심화 설명과 선택적 설정은 ▸ 접기/펼치기 영역에 넣었습니다.

02. 권장 기술 스택 및 사전 점검

2-1. 2026년 10월 기준 권장 이미지

구분 설정
서버 이름 alphagpu
호스트 운영체제 Ubuntu 26.04 LTS
GPU NVIDIA GeForce RTX 5090
NVIDIA 기본 이미지 nvcr.io/nvidia/pytorch:26.09-py3
컨테이너 내부 운영체제 Ubuntu 24.04
CUDA 13.4.1
Python 3.12
PyTorch NVIDIA 2.14.0a0 빌드 계열
프로젝트 실행 Docker Compose V2 (docker compose)

중요: 호스트 OS와 컨테이너 OS는 버전이 같을 필요가 없습니다. Ubuntu 26.04 호스트에서 Ubuntu 24.04 기반 이미지를 실행할 수 있습니다. NVIDIA NGC의 26.09 이미지는 2026-10-20 기준 공식 최신 태그이지만, 최신 프레임워크 빌드이므로 프로젝트별 라이브러리 호환성 검증이 필요합니다.

CUDA 13.4에 대응하는 드라이버 계열은 R615입니다. CUDA 13.x의 일부 하위 버전 호환성은 존재하지만, 최신 기능과 확실한 호환성을 위해 관리자와 R615 이상 드라이버 사용을 우선 검토합니다. 특히 컨테이너 이미지를 최신으로 바꾼다고 서버 GPU 드라이버가 자동으로 업데이트되지는 않습니다.

서버 관리자를 위한 사전 점검·설치 명령 보기

다음 명령은 서버 접속 후 버전과 GPU 상태를 확인하는 용도입니다.

cat /etc/os-release
nvidia-smi
docker --version
docker compose version
nvidia-ctk --version

nvidia-smi에 RTX 5090이 보이는지 확인합니다. 화면의 CUDA Version은 주로 드라이버가 지원하는 CUDA 최대 버전을 나타내며, 호스트에 CUDA Toolkit 전체가 설치되어 있다는 뜻은 아닙니다.

공용 서버에 Docker와 NVIDIA Container Toolkit이 없거나 GPU 런타임이 정상 연결되지 않았다면 관리자가 공식 설치 문서에 따라 구성해야 합니다. 이미 여러 프로젝트가 운영 중인 서버라면 아래 명령을 연구원 개인이 임의로 실행하지 않습니다.

# 서버 관리자만, NVIDIA Container Toolkit 설치 완료 후 실행
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker

Docker가 사용 가능한지, GPU를 컨테이너에 전달할 수 있는지는 관리자가 먼저 검증합니다. Docker의 docker 그룹 권한은 사실상 높은 호스트 권한으로 이어질 수 있으므로 사용자는 승인된 권한으로만 작업합니다.

06. Docker 프로젝트 파일 구성

프로젝트 루트는 다음과 같이 구성합니다. 이번 템플릿에서 꼭 필요한 파일은 Dockerfile, compose.yaml, requirements.txt입니다.

image-classification/
├── Dockerfile           # 컨테이너에 설치할 실행 환경

07. Dockerfile 작성 및 설명

프로젝트 루트에 Dockerfile을 생성합니다.

FROM nvcr.io/nvidia/pytorch:26.09-py3

WORKDIR /workspace

COPY requirements.txt /tmp/requirements.txt
RUN python -m pip install --no-cache-dir -r /tmp/requirements.txt

CMD ["bash"]

각 줄의 의미는 다음과 같습니다.

  • FROM: CUDA·cuDNN·PyTorch·Python이 포함된 NVIDIA NGC 이미지를 사용합니다. Ubuntu나 CUDA를 처음부터 별도로 설치하지 않습니다.
  • WORKDIR: 컨테이너 내부 작업 디렉터리를 /workspace로 정합니다.
  • COPY: 추가 패키지 목록을 이미지 안으로 복사합니다.
  • RUN: 이미지 빌드 시 패키지를 설치합니다. 실행할 때마다 pip install하지 않습니다.
  • CMD: 기본 실행 명령입니다. 아래 Compose의 command가 있으면 Compose 설정이 우선합니다.

기존 Dockerfile에 들어 있었던 EXPOSE 9696과 Jupyter 자동 실행 명령은 기본 템플릿에서 제거했습니다. 포트가 꼭 필요한 프로젝트에서만 설정하는 편이 안전하고 이해하기 쉽습니다.

추가 Python 패키지(requirements.txt) 설명 보기 
# 기존 프로젝트에서 사용했던 패키지의 예시
timm
mmengine
rasterio

기존 Dockerfile의 timm==0.5.4는 구형 버전이므로 최신 PyTorch·Python에서의 호환성을 검증하지 않은 상태로 강제 적용하지 않습니다. 위 파일은 패키지 설치 예시이며, 모든 조합의 빌드 성공을 보장하는 고정 버전 목록은 아닙니다. 실제 실험에서 검증한 버전은 프로젝트별로 명시적으로 고정하는 것을 권장합니다.

또한 최신 NVIDIA NGC 이미지에는 /etc/pip/constraint.txt에 기존 구성요소의 버전 제약이 포함됩니다. pip 의존성 충돌이 발생하면 기존 PyTorch/CUDA 구성요소를 무턱대고 업그레이드하지 말고 제약과 패키지 호환성을 먼저 확인합니다.

08. compose.yaml 작성 및 설명

compose.yaml은 한 프로젝트에 개발용 서비스 하나만 생성하는 간결한 형태로 작성합니다.

name: yuhan-image-classification

services:
  dev:
    build: .
    gpus: all
    shm_size: "8gb"
    user: "${LOCAL_UID}:${LOCAL_GID}"
    environment:
      HOME: /workspace
    working_dir: /workspace
    volumes:
      - .:/workspace
      # - /home/yuhan/projects/old-project:/reference/old-project:ro
      # - /nas1/datasets:/data/datasets:ro
    command: sleep infinity
설정 설명
name 사용자명 + 프로젝트명으로 Docker 리소스를 구분
build: . 현재 디렉터리의 Dockerfile로 이미지를 빌드
gpus: all 호스트에서 제공하는 NVIDIA GPU 장치 접근 활성화
shm_size DataLoader 등에 사용할 공유 메모리 크기 지정
user 본인 계정과 동일한 UID/GID로 실행해 파일 소유권 문제 감소
HOME 작업 및 캐시의 기본 홈 위치를 쓰기 가능한 작업공간으로 지정
working_dir 컨테이너 안의 기본 작업 위치
volumes 호스트 프로젝트·필요한 데이터 경로만 연결
command 컨테이너를 유지하고 필요할 때 명령을 실행하기 위한 기본 프로세스

gpus: all은 GPU를 해당 컨테이너에 독점 할당하는 설정이 아닙니다. 다른 연구원도 같은 GPU를 사용할 수 있으므로 장시간 작업 전 nvidia-smi로 사용량을 확인하고 연구실의 자원 배분 정책을 따릅니다.

참고: Compose는 Dockerfile을 직접 실행하는 명령이 아닙니다. build: .를 통해 이미지를 만들고, 그 이미지로 dev 컨테이너를 띄웁니다. docker compose exec dev ...는 이미 실행 중인 그 컨테이너 안에서 명령을 수행합니다.

처음 한 번: UID/GID와 .env 설정 펼치기

공동 서버에서는 컨테이너가 생성한 결과 파일이 root 소유로 남는 일이 발생할 수 있습니다. 이를 줄이기 위해 프로젝트 폴더에서 다음 명령으로 .env를 생성합니다.

printf 'LOCAL_UID=%s\nLOCAL_GID=%s\n' "$(id -u)" "$(id -g)" > .env

이 명령은 새 프로젝트의 .env를 처음 생성할 때만 사용합니다. 기존 .env가 있다면 덮어쓰지 말고 LOCAL_UID, LOCAL_GID 항목을 추가하세요. 이 파일은 실행 옵션을 채우기 위한 로컬 설정이므로 Git에 올리지 않습니다. user: 설정을 사용하는 템플릿에서는 실행 전에 .env가 필요합니다. 컨테이너 내부 시스템 패키지 설치처럼 관리자 권한이 필요한 작업은 Dockerfile의 빌드 단계에서 처리합니다.

첫 실행 직전, 명령어를 입력할 위치

아래 명령어는 서버 alphagpu의 터미널에서 입력합니다. 반드시 compose.yaml이 있는 프로젝트 폴더로 먼저 이동하세요.

cd ~/projects/image-classification
pwd
ls Dockerfile compose.yaml requirements.txt

파일이 없다고 나오면 06~08장의 템플릿 파일을 먼저 생성하세요. 기존 .env가 있다면 덮어쓰지 않습니다.

09. Docker Compose 실행 및 GPU 검증

9-1. 설정 확인과 첫 실행

cd ~/projects/image-classification

docker compose config
docker compose up -d --build

최초 빌드 때는 NGC 이미지를 다운로드하므로 시간이 오래 걸릴 수 있습니다. Docker 또는 NVIDIA Container Toolkit 설정에 오류가 있다면 서버 관리자에게 문의합니다.

9-2. GPU 확인

docker compose exec dev nvidia-smi

docker compose exec dev python -c \
  'import torch; print(torch.__version__); print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0))'

torch.cuda.is_available()이 True이고 GPU 이름이 표시되면 기본 CUDA 연결을 확인한 것입니다. 이 단계는 GPU가 연결되었다는 검증이며, 모든 학습 코드가 호환된다는 보장은 아닙니다.

9-3. 연구 코드 실행

# 컨테이너의 Shell 접속
docker compose exec dev bash

# 호스트 터미널에서 코드 한 번 실행
docker compose exec dev python train.py

# 로그 및 상태 확인
docker compose ps
docker compose logs --tail=100 dev

# 작업 종료
docker compose down

docker compose down은 현재 프로젝트의 컨테이너와 네트워크를 정리하지만, 호스트에서 bind mount한 프로젝트 파일이나 NAS 파일을 삭제하지는 않습니다. 다만 컨테이너 안에만 저장한 파일은 사라질 수 있으므로 결과는 /workspace처럼 연결된 경로에 저장해야 합니다.

10. 기존 프로젝트와 NAS 데이터 연결

볼륨(Volume)은 호스트의 폴더를 컨테이너의 특정 위치에서 보이도록 연결하는 설정입니다. 기본값은 현재 프로젝트만 연결하며, 기존 자료가 필요한 경우에만 경로를 추가합니다.

이전 프로젝트를 읽기 전용으로 연결하는 예시 보기

다음 중 프로젝트에 필요한 최소 범위만 연결합니다.

volumes:
  - .:/workspace
  - /home/yuhan/projects/old-project:/reference/old-project:ro

예를 들어 과거 프로젝트의 파일을 컨테이너에서 /reference/old-project로 읽을 수 있습니다. 부득이하게 홈 디렉터리 전체가 필요하다면 다음과 같이 작성할 수 있지만 권장하지 않습니다.

volumes:
  - .:/workspace
  - /home/yuhan:/reference/yuhan:ro

홈 전체에는 .ssh, 인증 정보, 개인 설정 등이 포함될 수 있습니다. :ro는 마운트 경로에 쓰기를 막는 옵션이지, 민감한 파일의 읽기 노출까지 막아 주지는 않습니다. 따라서 실제 운영에서는 필요한 하위 폴더만 연결하는 것이 원칙입니다.

NAS 데이터를 연결하는 예시 보기 
volumes:
  - .:/workspace
  - /nas1/datasets:/data/datasets:ro

컨테이너 안에서는 /data/datasets 경로로 데이터를 읽습니다. 예시 경로가 실제 서버에 존재하는지, 사용자의 읽기 권한이 있는지 먼저 확인합니다. 학습 결과 저장이 필요하다면 원본 데이터 경로를 읽기 전용으로 유지하고, 별도의 쓰기 가능한 출력 디렉터리를 사용합니다.

volumes:
  - .:/workspace
  - /nas1/datasets:/data/datasets:ro
  - /home/yuhan/projects/image-classification/outputs:/outputs

반대로 /:/host_root, privileged: true, ipc: host와 같은 과도한 호스트 접근 설정은 기본 템플릿에 넣지 않습니다. shm_size가 부족한 구체적인 상황에만 별도 조정을 검토합니다.

11. 라이브러리 업데이트와 코드 관리

새 라이브러리는 실행 중인 컨테이너에서 일시적으로 설치하는 대신 requirements.txt에 추가한 뒤 이미지를 다시 빌드합니다.

# requirements.txt 수정 후
docker compose up -d --build

# 코드와 설정 변경사항 확인
git status
git add Dockerfile compose.yaml requirements.txt train.py
git commit -m "Add GPU Docker development template"
git push

.env, 데이터셋, 대용량 모델 파일, 토큰, 인증키는 Git에 포함하지 않습니다. 필요한 항목은 .gitignore 및 .dockerignore에서 제외합니다. 재현성이 중요한 프로젝트는 검증한 패키지 버전을 고정하고, 변경 이력을 Commit으로 남깁니다.

12. 선택 사항: JupyterLab 접속

NVIDIA PyTorch 이미지에는 JupyterLab이 포함되어 있습니다. 다만 공동 서버에서 Jupyter를 불필요하게 외부 공개하지 않도록 SSH 포트 포워딩을 권장합니다.

compose.yaml의 dev 서비스에 다음 포트 매핑을 필요할 때만 추가합니다. 18888은 서버 내 다른 사용자와 겹치지 않는 포트로 변경하세요.

ports:
  - "127.0.0.1:18888:8888"

# 서버에서 변경한 Compose 설정 적용
docker compose up -d

# 서버에서 Jupyter 실행 (터미널 유지)
docker compose exec dev jupyter lab \
  --ip=0.0.0.0 --port=8888 --no-browser

로컬 PC의 새 터미널에서 다음 명령을 실행합니다.

ssh -L 8888:127.0.0.1:18888 yuhan@alphagpu

이후 로컬 브라우저에서 http://127.0.0.1:8888에 접속합니다. Jupyter가 출력한 토큰을 사용하며 인증을 끄지 않습니다. 사용자별 서버 포트와 로컬 포트가 충돌하지 않도록 주의합니다.

13. 자주 발생하는 문제와 체크리스트

자주 발생하는 문제

Q. docker compose 명령을 찾을 수 없습니다.
→ Docker Compose V2 플러그인이 설치되어 있는지 확인하고 관리자에게 문의합니다. 최신 문서의 명령은 docker-compose가 아니라 docker compose입니다.

Q. torch.cuda.is_available()이 False입니다.
→ 호스트 nvidia-smi, NVIDIA 드라이버 버전, NVIDIA Container Toolkit 설치 및 Docker GPU 런타임 설정을 확인합니다.

Q. pip install이 충돌하거나 빌드가 실패합니다.
→ NGC 이미지의 기본 PyTorch와 /etc/pip/constraint.txt 제약, 프로젝트 패키지 호환성을 확인합니다. 기존 PyTorch를 임의로 덮어쓰지 않습니다.

Q. 작업 결과 파일의 소유자가 이상합니다.
→ .env의 LOCAL_UID, LOCAL_GID가 실제 계정의 id -u, id -g와 일치하는지 확인합니다. 이미 생성된 파일의 소유권은 관리 정책에 따라 별도로 정리해야 할 수 있습니다.

Q. NAS 폴더가 컨테이너에 보이지 않습니다.
→ NAS가 호스트에 실제로 마운트되어 있는지, 해당 경로가 존재하는지, Unix 파일 권한을 확인합니다. 마운트가 없다고 해서 임의로 시스템 경로를 생성하지 않습니다.
